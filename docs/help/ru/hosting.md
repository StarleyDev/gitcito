# Хостинги и пул-реквесты

## Создание

Создавайте пул-реквест (или мёрж-реквест), не выходя из приложения: выпадающие
списки веток, заголовок и описание, предзаполненные из коммитов ветки,
переключатель черновика и — на GitHub — ревьюеры, метки и исполнители,
проставляемые прямо при создании.

![Создание пул-реквеста](../../screenshots/create-pr.webp)

Работает с **GitHub, GitLab, Bitbucket и Azure DevOps**. Открытые PR/MR всех
четырёх перечислены в боковой панели.

Начать можно из сравнения веток, из графа, по `+` в панели PR или из задачи
(тогда подставится `Closes #N`).

## Стеки в списке

Pull request’ы, стоящие друг на друге, сворачиваются в одну строку: значок
стека, ветка, на которую приземляется цепочка, и сколько их. Разверните — и
увидите цепочку в порядке чтения, от вершины к основанию, а под каждой строкой
маленькую стрелку с тем, во что она вливается: направление на экране, а не
выводится из четырёх баз.

Группу задают две вещи: собственный номер стека GitHub, если pull request’ы
входят в [нативный стек](stacks.md), а иначе сами ссылки — pull request, чья база
это голова другого, стоит на нём. Второе правило и делает это работающим на
GitLab, Bitbucket и Azure DevOps.

![Стек в списке pull request’ов](../../screenshots/pr-stack-list.webp)

В каждой строке — состояние **проверок** её головы (наведите, чтобы увидеть
числа), а на GitHub ещё и уровни, уже закрытые или влитые, которые список
открытых PR скрыл бы. Уровень над **закрытым** помечается заблокированным: его
собственные проверки могут быть зелёными, но ветка, на которую он нацелен, уже
никогда не приземлится. Действия строки появляются при наведении, чтобы заголовку
хватало ширины.

Чтение проверок стоит один запрос на pull request и только при обновлении
списка.

## Ваши pull request’ы в родительском репозитории форка

В форке важны обычно те pull request’ы, которые вы открыли в репозитории, от
которого сделан форк, а живут они там, а не в вашем форке. Поэтому, если у
репозитория есть удалённый `upstream`, указывающий на другой репозиторий GitHub,
чем `origin`, список также запрашивает у `upstream` открытые pull request’ы и
оставляет **только те, чья ветка пришла из вашего форка**. Они показываются под
pull request’ами форка, под заголовком с именем родителя, **В owner/repo**. Клик
открывает тот же экран подробностей, с проверками и ревью, в родительском
репозитории.

![Собственный pull request форка, а под ним его pull request’ы в родителе, под On example/pr-ready-branch](../../screenshots/fork-upstream-prs.webp)

*Ограничения:* только GitHub и только удалённый с именем `upstream`. Остальные
pull request’ы родителя намеренно не показываются: это его очередь, а не ваша
работа. Стеки и поиск веток по-прежнему работают только со списком `origin`.
Запрос к родителю — это ещё один запрос при каждом обновлении.

## Ревью — GitHub и GitLab

| | |
|---|---|
| **Обсуждение** | Комментарии и состояние ревью |
| **Проверки** | Прогоны CI (GitHub) или задания пайплайна (GitLab) со статусами успех/провал/в процессе и ссылками на логи |
| **Просмотренные файлы** | Чек-лист с ✓ по каждому файлу и прогрессом |
| **Ветки комментариев** | Комментарии к строкам, сгруппированные по `file:line`, и ответы |
| **Действия** | Комментировать, одобрить, запросить изменения, а также merge / squash |

Если кто-то делает форс-пуш посреди ревью, [что изменилось с прошлого
раза](range-diff.md) покажет вам ровно то, что сдвинулось.

Отличия GitLab, названные прямо: у GitLab нет единого вызова «отправить
ревью», поэтому **одобрить** использует его эндпоинт одобрений, а **запросить
изменения** снимает ваше одобрение и публикует ваш комментарий. **Rebase-merge**
не предлагается — GitLab сам выбирает между merge-коммитом и fast-forward по
настройкам проекта, поэтому в меню мёржа только merge и squash. Ветки
комментариев показывают файл и строку, но не окружающий ханк диффа: API GitLab
его не возвращает. Ревью и мёрж работают для проектов на **gitlab.com**;
self-hosted-инстансы пока не поддерживаются. Bitbucket и Azure DevOps для ревью
по-прежнему открываются в браузере.

## GitLab на собственном сервере

У корпоративного GitLab свой адрес. Укажите его в профиле в **Настройки →
Интеграции → GitLab → Адрес GitLab**, например `git.example.org` или
`https://example.net/gitlab` для экземпляра под путём. С этого момента удалённые
на этом хосте — это GitLab: merge request’ы показываются, открываются,
ревьюятся и сливаются, браузер клонирования и *Создать репозиторий* работают с
ним, а push и fetch входят с токеном этого профиля.

**Токен GitLab принадлежит одному экземпляру.** Токен профиля отправляется только
на адрес, указанный в этом профиле. Пустой адрес означает gitlab.com. Токен
gitlab.com никогда не попадает на корпоративный сервер, а корпоративный — на
gitlab.com. Если рабочая и личная учётные записи на разных экземплярах, дайте
каждой свой профиль. Репозиторий, привязанный к профилю, использует экземпляр
этого профиля.

**Создать токен** открывает страницу токенов вашего экземпляра с уже выбранными
`api` и `write_repository`. Токен только для чтения подключается без проблем, а
затем падает на первом push.

Ограничения:

- **Только https.** Адрес `http://` отклоняется, потому что токен шёл бы по сети
  открытым текстом.
- **Один экземпляр GitLab на профиль.** Для второго экземпляра добавьте второй
  профиль.
- По ssh сравнивается хост, а не путь, поэтому два экземпляра на одном хосте с
  разными путями для ssh-удалённого не различить.
- Аватары удалённых рисуются только для gitlab.com и github.com. Удалённый на
  собственном сервере получает простой значок, чтобы имена его групп никогда не
  уходили на публичный хост.

## Forgejo

Укажите адрес экземпляра до ввода его токена. Смена адреса сбрасывает предыдущий вход.

![Настройки интеграции с Forgejo](../../screenshots/forgejo-integration.webp)

Forgejo — и Gitea, у которой тот же API, — всегда работает по адресу, выбранному
владельцем: ваш собственный сервер или публичный, например codeberg.org. Укажите
этот адрес в профиле в **Настройки → Интеграции → Forgejo** вместе с токеном
доступа. **Создать токен** открывает страницу токенов этого сервера. Дайте токену
чтение и запись для *repository* и чтение для *user* и *organization*.

С этого момента удалённые на этом сервере — это Forgejo:

| Работает | Как |
|----------|-----|
| Push и fetch | Вход с токеном профиля |
| Открытые pull request’ы | В списке боковой панели, открываются на [странице pull request’а](#ревью--github-и-gitlab): обсуждение, diff каждого файла, проверки (статусы коммита, включая Forgejo Actions), комментарий, одобрение, запрос изменений, а также merge / squash / rebase |
| Создание pull request’а | Из приложения; черновик получает префикс `WIP:`, который использует Forgejo |
| Браузер клонирования, создание репозитория | На этом сервере, под вашей учётной записью или в организации |

Как и с GitLab, **токен Forgejo уходит только на сервер, который его выдал**. У
профиля без адреса Forgejo нет никаких учётных данных Forgejo. Сервера по
умолчанию, на который можно было бы откатиться, нет.

Ограничения:

- Ветки комментариев к строкам показываются, но ответить в них из приложения
  нельзя: у Forgejo нет API для ответа внутри существующей ветки. Отвечайте на
  сервере.
- Только https, один сервер Forgejo на профиль.
- Списки показывают первые 50 pull request’ов и репозиториев.

## Задачи, вехи, релизы — GitHub

Просматривайте задачи и открывайте полноценную вкладку задачи: описание,
комментарии, метки, исполнители, веха, поля Projects v2, закрытие/переоткрытие и
**создать ветку под эту задачу** (с именованием через ИИ). У вех показывается
прогресс и их задачи. Релизы просматриваются вместе со страницей changelog.

## Ждут вашего ревью

В списке pull request’ов на боковой панели значок 👁 отмечает PR, где **вы** —
ревьюер и ещё не ответили, — на GitHub, GitLab и Forgejo одинаково. Кто такие
«вы», приложение узнаёт у хоста по учётным данным профиля и помнит десять минут.
Токен, который не может прочитать собственного пользователя (например, без
`read:user` в Forgejo), ничего не отмечает.

## Уведомления — GitHub

Весь ваш входящий поток — запросы на ревью, упоминания, активность CI — по всем
репозиториям сразу, с фильтрами непрочитанное/все и отметкой о прочтении. На
колокольчике в панели инструментов висит счётчик непрочитанных, а по желанию
приходят и системные уведомления, когда у вас запросили ревью или закончился CI.

## Токены

Токены на профиль для нескольких аккаунтов или организаций, хранящиеся в связке
ключей вашей ОС. Gitcito умеет также одолжить то, что уже держит ваш
**git credential helper**, так что организации, для которой вы уже
аутентифицировались, часто вообще не нужна никакая настройка. Смотрите
[Безопасность и секреты](security.md).

Каждый профиль **привязывает свою учётную запись**. В Настройки → Интеграции
кнопка **Войти через git** ищет вход, который уже есть на компьютере, — в
credential helper git, затем активную учётную запись **GitHub CLI**, затем окно
входа самого helper — и привязывает эту учётную запись к профилю. Ничего не
делится неявно: новый профиль начинает без подключения, а учётная запись, уже
привязанная к другому профилю, отклоняется. Чтобы привязать вторую учётную
запись GitHub, добавьте её в gh (`gh auth login`), сделайте активной
(`gh auth switch`) и войдите из другого профиля — или вставьте токен этой
учётной записи. Git никогда не спрашивает имя пользователя и пароль в терминале.

Страница показывает, что используется для подключения — токен профиля, его
привязка к helper git или к GitHub CLI, а **Отключить** отменяет это только для
этого профиля: токен удаляется (на сервисе он действует, пока вы его там не
отзовёте), привязка снимается (вход остаётся в gh или в helper).

И API сервиса — pull request'ы, issues, CI, — и fetch, pull и push самого git по
https используют токен или привязанную учётную запись профиля. Учётные данные
попадают в git только для этой одной команды, только для хоста удалённого
репозитория, и никогда не записываются в `.git/config`. Профиль без того и
другого оставляет git его собственному credential helper. Azure DevOps, GitLab
и Bitbucket привязываются через credential helper git — Git Credential Manager
хранит несколько учётных записей на сервис — или используют токен на профиль.
Привязка указывает одну учётную запись на сервис, поэтому организациям с
разными учётными записями нужен отдельный профиль для каждой.
