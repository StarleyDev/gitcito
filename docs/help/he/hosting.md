# אירוח ובקשות משיכה

## יצירה

צרו בקשת משיכה (או מיזוג) בלי לצאת מהאפליקציה: רשימות ענפים נפתחות, כותרת וגוף
שממולאים מראש מהקומיטים של הענף, מתג טיוטה, וב־GitHub גם סוקרים, תוויות ומשויכים
שמוחלים בעת היצירה.

![יצירת בקשת משיכה](../../screenshots/create-pr.webp)

עובד ב־**GitHub, GitLab, Bitbucket ו־Azure DevOps**. בקשות פתוחות בכל הארבעה
מופיעות בסרגל הצד.

התחילו אחת מהשוואת ענפים, מהגרף, מה־`+` בפאנל בקשות המשיכה, או מתוך בעיה (שממלאת
`Closes #N`).

## ערימות ברשימה

Pull requests שיושבים זה על זה מתקפלים לשורה אחת עם סמל ערימה, הענף שעליו
השרשרת נוחתת, וכמה יש. פתחו אותה כדי לראות את השרשרת בסדר הקריאה — מהעלה למטה עד הבסיס — עם חץ קטן מתחת
לכל שורה שאומר לאן היא ממוזגת, כך שהכיוון על המסך ולא מוסק מארבעה בסיסים.

שני דברים יוצרים את הקבוצה: מספר הערימה של GitHub עצמו, כשה־pull requests שייכים
ל[ערימה מובנית](stacks.md), ואחרת ה־refs עצמם — pull request שהבסיס שלו הוא
ה־head של אחר יושב עליו. הכלל השני הוא הסיבה שזה עובד גם ב־GitLab, ב־Bitbucket
וב־Azure DevOps.

![ערימה ברשימת ה־pull requests](../../screenshots/pr-stack-list.webp)

כל שורה נושאת את מצב ה**בדיקות** של ה־head שלה — ריחוף מציג את המספרים — וב־GitHub
גם את השכבות שכבר נסגרו או מוזגו, שרשימת PR פתוחים הייתה מסתירה. שכבה שמעל שכבה
**סגורה** מסומנת כחסומה: הבדיקות שלה עשויות להיות ירוקות, אבל הענף שהיא מכוונת אליו
כבר לא ינחת. פעולות השורה מופיעות בריחוף, כדי שהכותרת תשמור על הרוחב.

קריאת הבדיקות עולה בקשה אחת לכל pull request, ורק כשהרשימה מתרעננת.

## בקשות המשיכה שלכם במאגר המקור של fork

ב-fork, בקשות המשיכה שחשובות הן בדרך כלל אלה שפתחתם במאגר שממנו עשיתם fork, והן נמצאות
שם, לא ב-fork שלכם. לכן, כשלמאגר יש מרוחק `upstream` שמצביע על מאגר GitHub שונה
מ-`origin`, הרשימה שואלת גם את `upstream` על בקשות המשיכה הפתוחות שלו ושומרת **רק את אלה
שהענף שלהן מגיע מה-fork שלכם**. הן מופיעות מתחת לאלה של ה-fork, תחת כותרת עם שם מאגר
המקור, **ב-owner/repo**. לחיצה פותחת את אותה תצוגת פרטים, עם הבדיקות והסקירה, במאגר המקור.

![בקשת המשיכה של ה-fork עצמו, ומתחתיה בקשות המשיכה שלו במאגר המקור, תחת On example/pr-ready-branch](../../screenshots/fork-upstream-prs.webp)

*מגבלות:* GitHub בלבד, ורק מרוחק בשם `upstream`. שאר בקשות המשיכה של מאגר המקור מושמטות
בכוונה: זה התור שלו, לא העבודה שלכם. ערימות וחיפושי ענפים עדיין פועלים רק על הרשימה של
`origin`. רישום מאגר המקור עולה בקשה נוספת בכל רענון.

## סקירה — GitHub ו־GitLab

| | |
|---|---|
| **שיחה** | תגובות ומצב הסקירה |
| **בדיקות** | ריצות בדיקה של CI (GitHub) או משימות pipeline (GitLab) עם עבר/נכשל/ממתין וקישורים ללוגים |
| **קבצים שנצפו** | רשימת ✓ לכל קובץ עם התקדמות |
| **שרשורים בשורה** | תגובות שורה מקובצות לפי `file:line`, ותשובות |
| **פעולות** | תגובה, אישור, בקשת שינויים, ומיזוג / מעיכה |

אם מישהו דוחף בכוח באמצע הסקירה, [מה השתנה מאז](range-diff.md) מראה לכם בדיוק מה
זז.

ההבדלים של GitLab, בגלוי: ל־GitLab אין קריאה אחת של "שליחת סקירה", ולכן
**אישור** משתמש בנקודת הקצה של האישורים שלו, ו**בקשת שינויים** מסירה את האישור
שלכם ומפרסמת את התגובה שלכם. **מיזוג בריבייס** אינו מוצע — GitLab מחליט בין
קומיט מיזוג ל־fast-forward לפי הגדרות הפרויקט, ולכן תפריט המיזוג מציג רק מיזוג
ומעיכה. שרשורים בשורה מציגים את הקובץ ואת השורה אך לא את קטע הדיף שמסביב, שה־API
של GitLab אינו מחזיר. סקירה/מיזוג עובדים לפרויקטים ב־**gitlab.com**; מופעים
באירוח עצמי עדיין אינם נתמכים. Bitbucket ו־Azure DevOps עדיין נפתחים בדפדפן
לצורך סקירה.

## GitLab בניהול עצמי

ל-GitLab של חברה יש כתובת משלו. הזינו אותה בפרופיל תחת **הגדרות ← שילובים ← GitLab ←
כתובת GitLab**, למשל `git.example.org` או `https://example.net/gitlab` לשרת שמוגש תחת
נתיב. מאותו רגע, מרוחקים על אותו שרת הם GitLab: בקשות מיזוג מוצגות, נפתחות, נסקרות
וממוזגות, דפדפן השכפול ו*יצירת מאגר* מדברים איתו, ו-push ו-fetch נכנסים עם האסימון של
אותו פרופיל.

**אסימון GitLab שייך למופע אחד.** האסימון של פרופיל נשלח רק לכתובת שאותו פרופיל מציין.
כתובת ריקה פירושה gitlab.com. אסימון של gitlab.com לעולם לא מגיע לשרת החברה, ואסימון
של החברה לעולם לא מגיע ל-gitlab.com. אם חשבון העבודה והחשבון האישי נמצאים במופעים שונים,
תנו לכל אחד פרופיל משלו. מאגר שמקושר לפרופיל משתמש במופע של אותו פרופיל.

**יצירת אסימון** פותח את דף האסימונים של המופע שלכם עם `api` ו-`write_repository` מסומנים
מראש. אסימון לקריאה בלבד מתחבר בלי בעיה ואז נכשל ב-push הראשון.

מגבלות:

- **https בלבד.** כתובת `http://` פשוטה נדחית, כי האסימון היה עובר ברשת כטקסט גלוי.
- **מופע GitLab אחד לכל פרופיל.** הוסיפו פרופיל שני למופע שני.
- ב-ssh משווים את השרת ולא את הנתיב, כך ששני מופעים על אותו שרת בנתיבים שונים אינם ניתנים
  להבחנה במרוחק ssh.
- אווטארים של מרוחקים מצוירים רק עבור gitlab.com ו-github.com. מרוחק בניהול עצמי מקבל את
  הסמל הפשוט, כך ששמות הקבוצות שלו לעולם לא נשלחים לשרת ציבורי.

## Forgejo

הגדירו את כתובת המופע לפני הזנת האסימון שלו. שינוי הכתובת מוחק את הכניסה הקודמת.

![הגדרות השילוב עם Forgejo](../../screenshots/forgejo-integration.webp)

Forgejo — ו-Gitea, שחולק איתו את אותו API — תמיד רץ בכתובת שבעליו בחרו: השרת שלכם, או
שרת ציבורי כמו codeberg.org. הזינו את הכתובת בפרופיל תחת **הגדרות ← שילובים ← Forgejo**,
יחד עם אסימון גישה. **יצירת אסימון** פותח את דף האסימונים של אותו שרת. תנו לאסימון הרשאות
קריאה וכתיבה על *repository*, והרשאת קריאה על *user* ו-*organization*.

מאותו רגע, מרוחקים על אותו שרת הם Forgejo:

| עובד | איך |
|------|-----|
| Push ו-fetch | בכניסה עם האסימון של הפרופיל |
| בקשות משיכה פתוחות | מוצגות בסרגל הצד ונפתחות ב[דף בקשת המשיכה](#סקירה--github-וgitlab): השיחה, ה-diff של כל קובץ, בדיקות (סטטוסים של commit, כולל Forgejo Actions), תגובה, אישור, בקשת שינויים, ו-merge / squash / rebase |
| יצירת בקשת משיכה | מתוך האפליקציה; טיוטה מקבלת את הקידומת `WIP:` ש-Forgejo משתמש בה |
| דפדפן שכפול, יצירת מאגר | על אותו שרת, תחת החשבון שלכם או ארגון |

בדיוק כמו ב-GitLab, **אסימון Forgejo הולך רק לשרת שהנפיק אותו**. לפרופיל בלי כתובת
Forgejo אין שום פרטי כניסה ל-Forgejo. אין שרת ברירת מחדל ליפול אליו.

מגבלות:

- שרשורי תגובות על שורות מוצגים, אך אי אפשר להגיב בהם מהאפליקציה: ל-Forgejo אין API
  לתגובה בתוך שרשור קיים. הגיבו בשרת.
- https בלבד, שרת Forgejo אחד לכל פרופיל.
- הרשימות מציגות את 50 בקשות המשיכה והמאגרים הראשונים.

## בעיות, אבני דרך וריליסים — GitHub

דפדפו בבעיות ופתחו לשונית בעיה מלאה: גוף, תגובות, תוויות, משויכים, אבן דרך, שדות
Projects v2, סגירה/פתיחה מחדש, ו**יצירת ענף לבעיה הזו** (עם מתן שם בעזרת AI).
אבני דרך מציגות התקדמות ואת הבעיות שלהן. ריליסים ניתנים לדפדוף עם עמוד יומן
שינויים.

## ממתין לסקירה שלכם

ברשימת בקשות המשיכה בסרגל הצד, 👁 מסמן את ה-PR שבהם **אתם** סוקרים ועדיין לא הגבתם — ב-GitHub,
ב-GitLab וב-Forgejo כאחד. מי «אתם», נשאל מהשרת עם פרטי הכניסה של הפרופיל ונזכר לעשר דקות.
אסימון שאינו יכול לקרוא את המשתמש שלו (בלי `read:user` ב-Forgejo, למשל) לא מסמן דבר.

## התראות — GitHub

כל תיבת הדואר הנכנס שלכם — בקשות סקירה, אזכורים, פעילות CI — בכל המאגרים, עם
מסנני לא־נקרא/הכול וסימון כנקרא. הפעמון בסרגל הכלים נושא תג של לא־נקראות, והתראות
שולחן עבודה לבחירתכם נורות כשמתבקשת סקירה או כש־CI מסתיים.

## טוקנים

טוקנים לכל פרופיל עבור כמה חשבונות או ארגונים, נשמרים במחזיק המפתחות של מערכת
ההפעלה. Gitcito יכול גם לשאול את מה ש**עוזר האישורים** של git שלכם כבר מחזיק, ולכן
ארגון שכבר התאמתם מולו לרוב אינו דורש שום הגדרה. ראו
[אבטחה וסודות](security.md).

כל פרופיל **מקשר חשבון משלו**. בהגדרות → אינטגרציות, **התחברות באמצעות git** מחפש
התחברות שכבר קיימת במחשב — ב-credential helper של git, אחר כך בחשבון הפעיל של
**GitHub CLI**, ואחר כך בחלון ההתחברות של ה-helper עצמו — ומקשר את החשבון הזה
לפרופיל. שום דבר לא משותף במובלע: פרופיל חדש מתחיל מנותק, וחשבון שפרופיל אחר
כבר קישר נדחה. כדי לקשר חשבון GitHub שני, הוסיפו אותו ל-gh (`gh auth login`),
הפכו אותו לפעיל (`gh auth switch`) והתחברו מהפרופיל האחר — או הדביקו את האסימון
של החשבון הזה. git אף פעם לא מבקש שם משתמש וסיסמה בטרמינל.

הדף מציג אם החיבור הוא האסימון של הפרופיל, הקישור שלו ל-helper של git או הקישור
שלו ל-GitHub CLI, ו**ניתוק** מבטל זאת רק לפרופיל הזה: אסימון נמחק (הוא נשאר בתוקף
אצל הספק עד שתבטלו אותו שם), קישור מוסר (ההתחברות נשארת ב-gh או ב-helper).

גם ה-API של הספק — בקשות משיכה, issues, CI — וגם ה-fetch, ה-pull וה-push של git
עצמו ב-https משתמשים באסימון או בחשבון המקושר של הפרופיל. פרטי ההתחברות מגיעים
ל-git רק עבור הפקודה הזו, מוגבלים למארח של ה-remote, ולעולם לא נכתבים
ל-`.git/config`. פרופיל בלי אף אחד מהם משאיר את git עם ה-credential helper שלו.
Azure DevOps, GitLab ו-Bitbucket מתקשרים דרך ה-credential helper של git — Git
Credential Manager שומר כמה חשבונות לכל ספק — או משתמשים באסימון לכל פרופיל.
קישור מציין חשבון אחד לכל ספק, ולכן ארגונים שדורשים חשבונות שונים מקבלים פרופיל
נפרד לכל אחד.
