# 托管与拉取请求

## 创建

不用离开这个应用就能创建拉取请求（PR，在有些平台上叫合并请求）：分支下拉框、由该分支的提交预填好的标题和正文、一个草稿开关，以及——在 GitHub 上——创建时就一并设好的评审者、标签和指派人。

![创建一个拉取请求](../../screenshots/create-pr.webp)

**GitHub、GitLab、Bitbucket 和 Azure DevOps** 都能用。四家平台上打开着的 PR/MR 都列在侧边栏里。

可以从分支对比、提交图、PR 面板里的 `+`，或者从一个议题出发创建（后者会自动填上 `Closes #N`）。

## 列表里的堆栈

互相叠在一起的 PR 会折叠成一行：堆栈图标、这条链落脚的分支，以及一共几个。展开就能按阅读顺序看到整条链——从最上面一直到基底——每行下面还有个小箭头写着它合并进
哪里，方向直接摆在屏幕上，不用对着四个基底自己推。

决定它们成组的有两件事：如果这些 PR 属于[原生堆栈](stacks.md)，就用 GitHub 自己的堆栈编号；
否则看 ref 本身——基底是另一个 PR 的 head，就说明它压在那个上面。第二条规则正是它在 GitLab、
Bitbucket 和 Azure DevOps 上同样管用的原因。

![PR 列表里的堆栈](../../screenshots/pr-stack-list.webp)

每一行都带着它 head 的**检查**状态——悬停能看到数量——在 GitHub 上还会列出已经关闭或已
合并的层，这些在“只看开着的 PR”的列表里本来是看不到的。位于**已关闭**那层之上的层会被标
成受阻：它自己的检查也许是绿的，但它指向的分支永远不会落地了。行上的操作按钮悬停才出现，
好把宽度让给标题。

读取检查的代价是每个 PR 一个请求，而且只在刷新列表时发生。

## 你在 fork 上游仓库中的拉取请求

在 fork 中，重要的拉取请求通常是你在被 fork 的仓库里开的那些，它们在那边，而不在你的
fork 上。因此，当一个仓库有指向不同于 `origin` 的 GitHub 仓库的 `upstream` 远程时，列表
也会向 `upstream` 查询其打开的拉取请求，并**只保留分支来自你 fork 的那些**。它们显示在
你 fork 自己的拉取请求下方，位于写有上游名称的标题 **在 owner/repo 上** 之下。点击会在
上游打开同样的详情视图，包括检查和评审。

![fork 自己的拉取请求，下方是它在上游的拉取请求，位于 On example/pr-ready-branch 之下](../../screenshots/fork-upstream-prs.webp)

*限制：* 仅限 GitHub，且仅限名为 `upstream` 的远程。上游的其他拉取请求被有意排除：那是
上游的队列，不是你的工作。堆叠和分支查找仍只作用于 `origin` 的列表。列出上游会让每次
刷新多一次请求。

## 评审——GitHub 与 GitLab

| | |
|---|---|
| **对话** | 评论与评审状态 |
| **检查** | CI 检查任务（GitHub）或流水线作业（GitLab），带通过／失败／等待中状态和查看日志的链接 |
| **已看过的文件** | 每个文件一个 ✓ 的清单，带进度 |
| **行内讨论串** | 按 `file:line` 归组的行评论，以及回复 |
| **动作** | 评论、批准、要求修改，以及合并 / 压缩合并 |

如果有人在评审进行到一半时强制推送，[自那以后改了什么](range-diff.md)会准确告诉你哪些东西动了。

GitLab 的差别，直说了就是：GitLab 没有单一的“提交评审”调用，所以**批准**用的是它的批准接口，**要求修改**则会撤掉你的批准并发出你的评论。不提供**变基合并**——GitLab 会根据项目设置自行决定用合并提交还是快进，所以合并菜单里只有合并和压缩合并两项。行内讨论串会显示文件和行号，但不会显示周围的变更块，因为 GitLab 的 API 不返回它。评审／合并适用于 **gitlab.com** 上的项目；自托管实例暂不支持。Bitbucket 和 Azure DevOps 的评审仍会在浏览器中打开。

## 自管理 GitLab

公司的 GitLab 有自己的地址。在 **设置 → 集成 → GitLab → GitLab 地址** 中为配置档填写
该地址，例如 `git.example.org`，或在某个路径下提供服务时填 `https://example.net/gitlab`。
此后，该主机上的远程即为 GitLab：合并请求可列出、打开、评审和合并，克隆浏览器和
*创建仓库* 与它通信，push 和 fetch 用该配置档的令牌登录。

**GitLab 令牌只属于一个实例。** 配置档的令牌只会发送到该配置档填写的地址。地址为空表示
gitlab.com。gitlab.com 的令牌绝不会到达公司服务器，公司的令牌也绝不会到达 gitlab.com。
如果工作账号和个人账号在不同实例上，请各用一个配置档。绑定到某个配置档的仓库使用该配置档
的实例。

**创建令牌** 会打开你实例的令牌页面，并预先勾选 `api` 和 `write_repository`。只读令牌
可以正常连接，但会在第一次 push 时失败。

限制：

- **仅限 https。** 普通的 `http://` 地址会被拒绝，因为令牌会以明文经过网络。
- **每个配置档一个 GitLab 实例。** 第二个实例请添加第二个配置档。
- 通过 ssh 时比较的是主机而不是路径，因此同一主机上不同路径的两个实例，对 ssh 远程来说
  无法区分。
- 远程头像只为 gitlab.com 和 github.com 绘制。自管理远程使用普通图标，这样它的群组名称
  永远不会发送到公共主机。

## Forgejo

先设置实例地址，再输入它的令牌。更改地址会清除之前的登录。

![Forgejo 集成设置](../../screenshots/forgejo-integration.webp)

Forgejo——以及共享同一 API 的 Gitea——总是运行在其所有者选定的地址上：你自己的服务器，
或像 codeberg.org 这样的公共服务器。在 **设置 → 集成 → Forgejo** 中为配置档填写该地址，
以及一个访问令牌。**创建令牌** 会打开该服务器的令牌页面。请给令牌 *repository* 的读写
权限，以及 *user* 和 *organization* 的读取权限。

此后，该服务器上的远程即为 Forgejo：

| 可用功能 | 方式 |
|----------|------|
| Push 和 fetch | 使用配置档的令牌登录 |
| 打开的拉取请求 | 在侧边栏列出，并在[拉取请求页面](#评审github-与-gitlab)中打开：对话、每个文件的 diff、检查（提交状态，包括 Forgejo Actions）、评论、批准、请求修改，以及 merge / squash / rebase |
| 创建拉取请求 | 在应用中创建；草稿带有 Forgejo 使用的 `WIP:` 前缀 |
| 克隆浏览器、创建仓库 | 在该服务器上，归属你的账号或某个组织 |

和 GitLab 一样，**Forgejo 令牌只会发送到签发它的服务器**。没有 Forgejo 地址的配置档
没有任何 Forgejo 凭据。也没有可回退的默认服务器。

限制：

- 行评论讨论串会显示，但无法在应用中回复：Forgejo 没有在已有讨论串内回复的 API。请到
  服务器上回复。
- 仅限 https，每个配置档一个 Forgejo 服务器。
- 列表显示前 50 个拉取请求和仓库。

## 议题、里程碑、发布——GitHub

浏览议题，并打开一个完整的议题标签页：正文、评论、标签、指派人、里程碑、Projects v2 字段、关闭／重新打开，以及**为这个议题创建一个分支**（可由 AI 起名）。里程碑会显示进度和它下面的议题。发布可以连同变更日志页面一起浏览。

## 等待你的评审

在侧边栏的拉取请求列表中，👁 标记出**你**是评审者但尚未回应的 PR——GitHub、GitLab 和
Forgejo 都一样。“你”是谁，会用配置档的凭据向主机查询，并记住十分钟。无法读取自身用户的
令牌（例如 Forgejo 上没有 `read:user`）不会标记任何内容。

## 通知——GitHub

你的整个收件箱——评审请求、提及、CI 动态——覆盖每一个仓库，带未读／全部筛选和标记为已读。工具栏上的铃铛带一个未读徽标，还可以选择在有人请求评审或 CI 跑完时弹出桌面通知。

## 令牌

按配置档保存的令牌，可以对应多个账号或组织，存在你操作系统的钥匙串里。Gitcito 也可以直接借用你的 **git credential helper** 里已经有的凭据，所以一个你早就认证过的组织往往完全不需要配置。见[安全与机密](security.md)。

每个配置文件**关联它自己的账号**。在 设置 → 集成 中，**用 git 登录** 会查找
机器上已有的登录——先是 git 的 credential helper，然后是 **GitHub CLI** 的活动
账号，然后是 helper 自己的登录窗口——并把该账号关联到配置文件。不会有任何隐式
共享：新配置文件一开始是未连接的，已被其他配置文件关联的账号会被拒绝。要关联第二
个 GitHub 账号，请把它加入 gh（`gh auth login`），设为活动账号（`gh auth switch`），
再从另一个配置文件登录——或粘贴该账号的令牌。git 永远不会在终端里询问用户名和密码。

页面会显示连接使用的是配置文件的令牌、与 git helper 的关联，还是与 GitHub CLI 的
关联；**断开连接** 只对当前配置文件生效：令牌会被清除（在你于托管方撤销之前仍然
有效），关联会被移除（登录仍保留在 gh 或 helper 中）。

托管方的 API——拉取请求、议题、CI——以及 git 自身通过 https 的 fetch、pull 和
push，都使用配置文件的令牌或关联账号。凭据只为那一条命令、只针对远程仓库的主机
交给 git，永远不会写入 `.git/config`。两者都没有的配置文件，git 会使用它自己的
credential helper。Azure DevOps、GitLab 和 Bitbucket 通过 git 的 credential helper
关联（Git Credential Manager 可为每个托管方保存多个账号），或每个配置文件使用一个
令牌。一个关联对应每个托管方的一个账号，因此需要不同账号的组织应各用一个配置文件。
