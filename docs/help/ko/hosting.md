# 호스팅과 풀 리퀘스트

## 만들기

앱을 벗어나지 않고 풀 리퀘스트(또는 머지 리퀘스트)를 만들어요. 브랜치 드롭다운,
브랜치의 커밋으로 미리 채워진 제목과 본문, 초안 토글, 그리고 GitHub에서는
생성과 동시에 적용되는 리뷰어·라벨·담당자까지 있어요.

![풀 리퀘스트 만들기](../../screenshots/create-pr.webp)

**GitHub, GitLab, Bitbucket, Azure DevOps** 에서 동작해요. 네 곳 모두의 열린
PR/MR 이 사이드바에 나열돼요.

브랜치 비교, 그래프, PR 패널의 `+`, 또는 이슈에서 시작할 수 있어요. 이슈에서
시작하면 `Closes #N` 이 자동으로 채워져요.

## 목록 속의 스택

서로의 위에 얹힌 풀 리퀘스트는 스택 아이콘, 사슬이 착지하는 브랜치, 개수를 가진 한 줄로
접힙니다. 펼치면 사슬이 읽는 순서대로 — 잎에서 베이스까지 — 보이고, 각 줄 아래에는 무엇에
병합되는지 알려주는 작은 화살표가 붙습니다. 방향이 화면에 있으니 베이스 넷을 보고
추측하지 않아도 됩니다.

그 묶음을 정하는 것은 두 가지입니다. 풀 리퀘스트가 [네이티브 스택](stacks.md)에 속하면
GitHub 자신의 스택 번호이고, 아니면 ref 그 자체입니다 — 베이스가 다른 PR의 head인 것은 그
위에 얹혀 있습니다. 두 번째 규칙 덕분에 GitLab, Bitbucket, Azure DevOps에서도 똑같이
동작합니다.

![풀 리퀘스트 목록 속의 스택](../../screenshots/pr-stack-list.webp)

각 줄에는 head의 **체크** 상태가 붙습니다 — 개수는 마우스를 올리면 보입니다. 그리고
GitHub에서는 이미 닫히거나 병합된 레벨도 함께 나옵니다. 열린 PR 목록이라면 감춰졌을
것들이죠. **닫힌** 레벨 위의 레벨은 막힘으로 표시됩니다. 자기 체크는 초록일지 몰라도,
겨냥한 브랜치가 더는 착지하지 않으니까요. 줄의 동작 버튼은 마우스를 올릴 때 나타나서
제목이 폭을 지킵니다.

체크를 읽는 비용은 풀 리퀘스트당 요청 한 번이고, 목록을 새로 고칠 때뿐입니다.

## 포크 원본 저장소에 있는 내 풀 리퀘스트

포크에서 중요한 풀 리퀘스트는 대개 포크해 온 저장소에 연 것이고, 그것은 내 포크가 아니라
그쪽에 있습니다. 그래서 `origin`과 다른 GitHub 저장소를 가리키는 `upstream` 원격이 있는
저장소에서는, 목록이 `upstream`에도 열린 풀 리퀘스트를 묻고 **브랜치가 내 포크에서 온
것만** 남깁니다. 이들은 포크 자신의 풀 리퀘스트 아래, 원본 이름을 단 제목
**owner/repo에서** 아래에 나타납니다. 클릭하면 같은 상세 화면이 체크와 리뷰와 함께 원본
저장소에서 열립니다.

![포크 자신의 풀 리퀘스트와, 그 아래 On example/pr-ready-branch에 있는 원본 저장소의 풀 리퀘스트](../../screenshots/fork-upstream-prs.webp)

*제한:* GitHub만, 그리고 이름이 `upstream`인 원격만. 원본 저장소의 다른 풀 리퀘스트는
일부러 제외합니다. 그것은 원본의 대기열이지 내 작업이 아닙니다. 스택과 브랜치 조회는
여전히 `origin`의 목록만 사용합니다. 원본 목록을 가져오면 새로 고칠 때마다 요청이 하나 더
듭니다.

## 리뷰 — GitHub와 GitLab

| | |
|---|---|
| **대화** | 댓글과 리뷰 상태 |
| **체크** | 통과/실패/대기 상태와 로그 보기 링크가 있는 CI 체크 실행(GitHub) 또는 파이프라인 잡(GitLab) |
| **본 파일** | 파일별 ✓ 체크리스트와 진행률 |
| **인라인 스레드** | `file:line` 별로 묶인 줄 댓글과 답글 |
| **작업** | 댓글, 승인, 변경 요청, 그리고 머지 / 스쿼시 |

리뷰 중에 누군가 강제 푸시를 하면, [그동안 바뀐 것](range-diff.md)이 무엇이
움직였는지 정확히 보여 줘요.

GitLab의 차이를 솔직하게 말하면 이래요. GitLab에는 단일 "리뷰 제출" 호출이
없어서, **승인**은 승인 엔드포인트를 쓰고 **변경 요청**은 내 승인을 거두고
댓글을 올려요. **리베이스 머지**는 제공되지 않아요 — GitLab이 프로젝트 설정에
따라 머지 커밋과 fast-forward 중에서 결정하기 때문에, 머지 메뉴에는 머지와
스쿼시만 보여요. 인라인 스레드는 파일과 줄은 보여 주지만 주변 diff 헝크는 보여
주지 않는데, GitLab API가 그걸 돌려주지 않기 때문이에요. 리뷰/머지는
**gitlab.com** 의 프로젝트에서 동작하고, 자체 호스팅 인스턴스는 아직 지원하지
않아요. Bitbucket과 Azure DevOps는 리뷰할 때 여전히 브라우저로 열려요.

## 자체 관리형 GitLab

회사 GitLab은 자체 주소에 있습니다. 그 주소를 **설정 → 연동 → GitLab → GitLab 주소**에서
프로필에 지정하세요. 예: `git.example.org`, 경로 아래에서 제공된다면
`https://example.net/gitlab`. 그때부터 그 호스트의 원격은 GitLab입니다. 머지 리퀘스트를
나열·열기·리뷰·병합하고, 클론 브라우저와 *저장소 만들기*가 그 서버와 통신하며, push와
fetch는 그 프로필의 토큰으로 로그인합니다.

**GitLab 토큰은 하나의 인스턴스에 속합니다.** 프로필의 토큰은 그 프로필이 지정한 주소로만
전송됩니다. 주소가 비어 있으면 gitlab.com을 뜻합니다. gitlab.com 토큰은 회사 서버에 절대
닿지 않고, 회사 토큰은 gitlab.com에 절대 닿지 않습니다. 업무용과 개인용 계정이 서로 다른
인스턴스에 있다면 각각 프로필을 따로 만드세요. 프로필에 연결된 저장소는 그 프로필의
인스턴스를 사용합니다.

**토큰 만들기**는 `api`와 `write_repository`가 미리 선택된 상태로 인스턴스의 토큰 페이지를
엽니다. 읽기 전용 토큰도 연결은 되지만 첫 push에서 실패합니다.

제한:

- **https만.** 평문 `http://` 주소는 거부됩니다. 토큰이 암호화되지 않은 채 네트워크를
  지나가기 때문입니다.
- **프로필당 GitLab 인스턴스 하나.** 두 번째 인스턴스에는 두 번째 프로필을 추가하세요.
- ssh에서는 경로가 아니라 호스트로 비교하므로, 한 호스트의 서로 다른 경로에 있는 두
  인스턴스는 ssh 원격에서 구별할 수 없습니다.
- 원격 아바타는 gitlab.com과 github.com에서만 그립니다. 자체 관리형 원격은 기본 아이콘을
  받으므로 그룹 이름이 공개 호스트로 전송되지 않습니다.

## Forgejo

토큰을 입력하기 전에 인스턴스 주소를 설정하세요. 주소를 바꾸면 이전 로그인이 지워집니다.

![Forgejo 연동 설정](../../screenshots/forgejo-integration.webp)

Forgejo — 그리고 같은 API를 쓰는 Gitea — 는 항상 소유자가 정한 주소에서 실행됩니다. 내
서버이거나 codeberg.org 같은 공개 서버입니다. 그 주소를 액세스 토큰과 함께
**설정 → 연동 → Forgejo**에서 프로필에 지정하세요. **토큰 만들기**는 그 서버의 토큰
페이지를 엽니다. 토큰에 *repository* 읽기·쓰기, *user*와 *organization* 읽기 권한을
주세요.

그때부터 그 서버의 원격은 Forgejo입니다:

| 동작 | 방법 |
|------|------|
| push와 fetch | 프로필의 토큰으로 로그인 |
| 열린 풀 리퀘스트 | 사이드바에 나열되고 [풀 리퀘스트 페이지](#리뷰--github와-gitlab)에서 열림: 대화, 파일별 diff, 체크(Forgejo Actions를 포함한 커밋 상태), 댓글, 승인, 변경 요청, merge / squash / rebase |
| 풀 리퀘스트 만들기 | 앱에서. 초안에는 Forgejo가 쓰는 `WIP:` 접두사가 붙음 |
| 클론 브라우저, 저장소 만들기 | 그 서버에서, 내 계정 또는 조직 아래 |

GitLab과 마찬가지로 **Forgejo 토큰은 발급한 서버로만 갑니다**. Forgejo 주소가 없는
프로필에는 Forgejo 자격 증명이 전혀 없습니다. 대신 쓸 기본 서버도 없습니다.

제한:

- 줄 댓글 스레드는 표시되지만 앱에서 답글을 달 수는 없습니다. Forgejo에는 기존 스레드
  안에 답글을 다는 API가 없습니다. 서버에서 답하세요.
- https만, 프로필당 Forgejo 서버 하나.
- 목록은 요청 20번 후에 멈춥니다. 서버의 기본 페이지 크기라면 풀 리퀘스트나 저장소 1,000개입니다.

## 이슈, 마일스톤, 릴리스 — GitHub

이슈를 둘러보고 전체 이슈 탭을 열 수 있어요. 본문, 댓글, 라벨, 담당자,
마일스톤, Projects v2 필드, 닫기/다시 열기, 그리고 **이 이슈용 브랜치 만들기**
(AI 이름 짓기 포함)까지요. 마일스톤은 진행률과 그에 속한 이슈를 보여 줘요.
릴리스는 변경 기록 페이지와 함께 둘러볼 수 있어요.

## 내 리뷰 대기 중

사이드바의 풀 리퀘스트 목록에서 👁는 **내가** 리뷰어인데 아직 응답하지 않은 PR을
표시합니다 — GitHub, GitLab, Forgejo 모두 같습니다. "나"가 누구인지는 프로필의 자격
증명으로 호스트에 묻고 10분 동안 기억합니다. 자기 사용자 정보를 읽을 수 없는 토큰(예:
Forgejo에서 `read:user`가 없는 경우)은 아무것도 표시하지 않습니다.

## 알림 — GitHub

리뷰 요청, 멘션, CI 활동까지 모든 저장소에 걸친 받은 편지함 전체를 볼 수 있어요.
읽지 않음/전체 필터와 읽음 표시가 있고요. 툴바의 종에는 읽지 않음 배지가 붙고,
원한다면 리뷰가 요청되거나 CI가 끝났을 때 데스크톱 알림이 뜨게 할 수 있어요.

## 토큰

여러 계정이나 조직을 위한 프로필별 토큰이 OS 키체인에 저장돼요. Gitcito는
**git credential helper** 가 이미 갖고 있는 것을 빌려 쓸 수도 있어서, 이미
인증해 둔 조직이라면 설정이 아예 필요 없는 경우가 많아요.
[보안과 비밀](security.md)을 보세요.

각 프로필은 **자기 계정을 연결**합니다. 설정 → 통합의 **git으로 로그인**은
이미 컴퓨터에 있는 로그인을 찾습니다 — git의 credential helper, 그다음
**GitHub CLI**의 활성 계정, 그다음 helper 자체의 로그인 창 — 그리고 그 계정을
프로필에 연결합니다. 암묵적으로 공유되는 것은 없습니다. 새 프로필은 연결되지
않은 상태로 시작하고, 다른 프로필이 이미 연결한 계정은 거부됩니다. 두 번째
GitHub 계정을 연결하려면 gh에 추가하고(`gh auth login`), 활성 계정으로
바꾼 뒤(`gh auth switch`) 다른 프로필에서 로그인하세요 — 또는 그 계정의
토큰을 붙여 넣으세요. git은 터미널에서 사용자 이름과 비밀번호를 묻지 않습니다.

이 페이지는 연결이 프로필의 토큰인지, git helper와의 연결인지, GitHub CLI와의
연결인지 보여 주며, **연결 해제**는 이 프로필에서만 그것을 되돌립니다. 토큰은
지워지고(호스트에서 취소하기 전까지 유효합니다), 연결은 해제됩니다(로그인은
gh나 helper에 남습니다).

호스트의 API(풀 리퀘스트, 이슈, CI)와 https를 통한 git 자체의 fetch·pull·push
모두 프로필의 토큰이나 연결된 계정을 사용합니다. 자격 증명은 그 명령 하나를
위해서만, 원격 저장소의 호스트로 한정되어 git에 전달되며, `.git/config`에 기록되지
않습니다. 둘 다 없는 프로필은 git이 자체 credential helper를 쓰도록 둡니다. Azure
DevOps, GitLab, Bitbucket은 git의 credential helper(Git Credential Manager는
호스트마다 여러 계정을 보관합니다)로 연결하거나 프로필별 토큰을 사용합니다. 연결은
호스트마다 계정 하나를 가리키므로, 서로 다른 계정이 필요한 조직은 각각 별도의
프로필을 씁니다.
