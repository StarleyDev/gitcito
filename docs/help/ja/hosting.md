# ホスティングとプルリクエスト

## 作成

アプリを離れずにプル（またはマージ）リクエストを作成できます。ブランチのドロップ
ダウン、ブランチのコミットからあらかじめ埋められたタイトルと本文、ドラフトの
切り替え、そして GitHub ならレビュアー・ラベル・担当者を作成時にそのまま適用でき
ます。

![プルリクエストの作成](../../screenshots/create-pr.webp)

**GitHub、GitLab、Bitbucket、Azure DevOps** で動作します。4 つすべての未クローズの
PR / MR がサイドバーに並びます。

起点はブランチ比較、グラフ、PR パネルの `+`、あるいはイシュー（`Closes #N` が自動で
入ります）のどこからでも構いません。

## 一覧の中のスタック

互いの上に乗っているプルリクエストは、スタックのアイコン、鎖の着地先ブランチ、件数を持つ
1 行にたたまれます。開けば、鎖が読む順（葉から下のベースへ）で並び、各行の下には何にマージされるかを示す
小さな矢印が付きます。向きは画面に出ていて、4 つのベースから推測するものではありません。

そのまとまりを決めるものは二つ。プルリクエストが[ネイティブなスタック](stacks.md)に属する
場合は GitHub 自身のスタック番号、そうでなければ ref そのもの — 別のプルリクエストの head
をベースにしているものは、その上に乗っています。二つ目の規則があるおかげで、GitLab・
Bitbucket・Azure DevOps でも同じように働きます。

![プルリクエスト一覧の中のスタック](../../screenshots/pr-stack-list.webp)

各行には head の**チェック**の状態が付きます（数はホバーで）。GitHub では、開いている
プルリクエストの一覧なら隠れてしまう「すでにクローズ／マージされた」レベルも並びます。
**クローズ済み**のレベルより上は「ブロック」と印が付きます。自分のチェックが緑でも、
狙っているブランチが着地することはもうないからです。行の操作はホバーで現れ、そのぶん
タイトルが幅を保ちます。

チェックの読み取りはプルリクエスト 1 件につき 1 リクエスト、しかも一覧を更新したときだけ
です。

## フォーク元リポジトリにあるあなたのプルリクエスト

フォークで大事なのは、たいていフォーク元のリポジトリで開いたプルリクエストで、それは
あなたのフォークではなく向こうにあります。そこで、`origin` とは別の GitHub リポジトリを
指す `upstream` リモートがあるリポジトリでは、一覧が `upstream` にもオープンな
プルリクエストを問い合わせ、**ブランチがあなたのフォークから来ているものだけ**を残します。
それらはフォーク自身のものの下に、フォーク元の名前を示す見出し **owner/repo 上** の下で
表示されます。クリックすると、同じ詳細ビューがチェックとレビュー付きでフォーク元で開きます。

![フォーク自身のプルリクエストと、その下の On example/pr-ready-branch にあるフォーク元のプルリクエスト](../../screenshots/fork-upstream-prs.webp)

*制限:* GitHub のみ、かつ `upstream` という名前のリモートのみ。フォーク元のほかの
プルリクエストは意図的に除外しています。それはフォーク元のキューであり、あなたの作業では
ありません。スタックやブランチの検索は引き続き `origin` の一覧だけを使います。
フォーク元の一覧取得は、更新ごとにリクエストが 1 回増えます。

## レビュー — GitHub と GitLab

| | |
|---|---|
| **会話** | コメントとレビューの状態 |
| **チェック** | CI のチェック実行（GitHub）またはパイプラインジョブ（GitLab）と成功／失敗／保留、ログを開くリンク |
| **表示済みファイル** | ファイルごとの ✓ チェックリストと進捗 |
| **インラインスレッド** | `file:line` ごとにまとめられた行コメントと、返信 |
| **アクション** | コメント、承認、変更要求、そしてマージ／スカッシュ |

レビューの途中で誰かがフォースプッシュしても、[前回から何が変わったか](range-diff.md)
が動いた部分を正確に見せてくれます。

GitLab の違いをはっきり述べておきます。GitLab には単一の「レビューを送信」という
呼び出しがないため、**承認** は承認用エンドポイントを使い、**変更要求** はあなたの
承認を取り消してコメントを投稿します。**リベースマージ** は提供されません。GitLab
はプロジェクトの設定からマージコミットかファストフォワードかを決めるため、マージ
メニューに並ぶのはマージとスカッシュだけです。インラインスレッドはファイルと行を
表示しますが、GitLab の API が返さない周囲の差分ハンクは表示できません。レビューと
マージは **gitlab.com** 上のプロジェクトで動作し、セルフホストのインスタンスはまだ
サポートされていません。Bitbucket と Azure DevOps のレビューは引き続きブラウザーで
開きます。

## セルフマネージドの GitLab

社内の GitLab は独自のアドレスにあります。そのアドレスを **設定 → 連携 → GitLab →
GitLab のアドレス** でプロファイルに指定します。例: `git.example.org`、パス配下で
提供されているなら `https://example.net/gitlab`。以後、そのホスト上のリモートは GitLab
として扱われます。マージリクエストの一覧・表示・レビュー・マージ、クローンブラウザーと
*リポジトリを作成* がそのサーバーと通信し、push と fetch はそのプロファイルのトークンで
サインインします。

**GitLab のトークンは 1 つのインスタンスに属します。** プロファイルのトークンは、その
プロファイルが指定するアドレスにしか送られません。アドレスが空なら gitlab.com を意味します。
gitlab.com のトークンが社内サーバーに届くことはなく、社内のトークンが gitlab.com に届く
こともありません。仕事用と個人用のアカウントが別のインスタンスにあるなら、それぞれに
プロファイルを用意してください。プロファイルに紐づいたリポジトリは、そのプロファイルの
インスタンスを使います。

**トークンを作成** は、`api` と `write_repository` を選択済みの状態でインスタンスの
トークンページを開きます。読み取り専用のトークンでも接続はできますが、最初の push で
失敗します。

制限:

- **https のみ。** 素の `http://` アドレスは拒否されます。トークンが平文でネットワークを
  流れてしまうためです。
- **1 プロファイルにつき GitLab インスタンスは 1 つ。** 2 つ目のインスタンスには 2 つ目の
  プロファイルを追加してください。
- ssh ではパスではなくホストで照合するため、同じホスト上の別パスにある 2 つの
  インスタンスは、ssh リモートでは区別できません。
- リモートのアバターは gitlab.com と github.com でのみ描画します。セルフマネージドの
  リモートは素のアイコンになり、グループ名が公開ホストへ送られることはありません。

## Forgejo

トークンを入力する前にインスタンスのアドレスを設定してください。アドレスを変えると以前のサインインは消去されます。

![Forgejo 連携の設定](../../screenshots/forgejo-integration.webp)

Forgejo — と、同じ API を持つ Gitea — は常に所有者が選んだアドレスで動いています。
自分のサーバーか、codeberg.org のような公開サーバーです。そのアドレスをアクセストークンと
一緒に **設定 → 連携 → Forgejo** でプロファイルに指定します。**トークンを作成** はその
サーバーのトークンページを開きます。トークンには *repository* の読み書き、*user* と
*organization* の読み取り権限を与えてください。

以後、そのサーバー上のリモートは Forgejo として扱われます:

| できること | 方法 |
|------------|------|
| push と fetch | プロファイルのトークンでサインイン |
| オープンなプルリクエスト | サイドバーに一覧表示され、[プルリクエストのページ](#レビュー--github-と-gitlab)で開く: 会話、各ファイルの差分、チェック(Forgejo Actions を含むコミットステータス)、コメント、承認、変更依頼、merge / squash / rebase |
| プルリクエストの作成 | アプリから。下書きには Forgejo が使う `WIP:` 接頭辞が付く |
| クローンブラウザー、リポジトリの作成 | そのサーバー上で、あなたのアカウントか組織の下に |

GitLab と同様に、**Forgejo のトークンは発行したサーバーにしか送られません**。Forgejo の
アドレスがないプロファイルには、Forgejo の資格情報が一切ありません。フォールバック先の
既定サーバーもありません。

制限:

- 行コメントのスレッドは表示されますが、アプリから返信はできません。Forgejo には既存の
  スレッド内に返信する API がないためです。サーバー上で返信してください。
- https のみ、1 プロファイルにつき Forgejo サーバーは 1 つ。
- 一覧は最初の 50 件のプルリクエストとリポジトリを表示します。

## イシュー、マイルストーン、リリース — GitHub

イシューを一覧し、専用タブで開けます。本文、コメント、ラベル、担当者、マイルストーン、
Projects v2 のフィールド、クローズ／再オープン、そして **このイシュー用のブランチを
作成**（AI による命名つき）。マイルストーンは進捗とそこに属するイシューを表示し、
リリースは変更履歴ページ付きで閲覧できます。

## あなたのレビュー待ち

サイドバーのプルリクエスト一覧では、**あなた**がレビュアーでまだ応答していない PR に 👁 が
付きます — GitHub、GitLab、Forgejo のいずれでも。「あなた」が誰かは、プロファイルの資格情報で
ホストに問い合わせ、10 分間記憶します。自分のユーザーを読めないトークン(たとえば Forgejo で
`read:user` がない場合)では何も付きません。

## 通知 — GitHub

レビュー依頼、メンション、CI の動きまで含めた受信箱全体を、すべてのリポジトリを
横断して表示します。未読／すべての切り替えと既読化つき。ツールバーのベルには未読
バッジが付き、レビューを依頼されたときや CI が終わったときにデスクトップ通知を出す
こともできます。

## トークン

複数アカウントや組織のためのプロファイル単位のトークンを、OS のキーチェーンに保存
します。Gitcito は **git の資格情報ヘルパー** がすでに持っているものを借りることも
できるので、認証済みの組織なら設定が一切要らない場合も少なくありません。
[セキュリティと秘密情報](security.md) を参照してください。

各プロファイルは**それぞれ自分のアカウントを連携**します。設定 → 連携 の
**git でサインイン** は、すでにマシン上にあるログインを探します（git の
credential helper、次に **GitHub CLI** のアクティブなアカウント、次に helper
自身のサインイン画面）。見つかったアカウントをそのプロファイルに連携します。
暗黙の共有はありません。新しいプロファイルは未接続から始まり、ほかの
プロファイルがすでに連携したアカウントは拒否されます。2つ目の GitHub
アカウントを連携するには、それを gh に追加し（`gh auth login`）、アクティブに
して（`gh auth switch`）、もう一方のプロファイルからサインインします。または
そのアカウントのトークンを貼り付けます。git がターミナルでユーザー名と
パスワードを尋ねることはありません。

このページには、接続がプロファイルのトークン、git の helper との連携、
GitHub CLI との連携のどれなのかが表示され、**接続を解除** はこのプロファイル
だけを元に戻します。トークンは消去され（ホスト側で取り消すまで有効なまま
です）、連携は外されます（ログインは gh や helper に残ります）。

ホストの API（プルリクエスト、Issue、CI）も、https での git 自体の fetch・
pull・push も、プロファイルのトークンか連携したアカウントを使います。認証情報は
そのコマンドのためだけに、リモートのホストに限定して git に渡され、
`.git/config` に書き込まれることはありません。どちらもないプロファイルでは、
git は自身の credential helper を使います。Azure DevOps、GitLab、Bitbucket は
git の credential helper（Git Credential Manager はホストごとに複数のアカウントを
保持します）で連携するか、プロファイルごとのトークンを使います。連携はホストごとに
1つのアカウントを指すため、別々のアカウントが必要な組織はそれぞれ別の
プロファイルにします。
